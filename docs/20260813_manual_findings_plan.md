## #4 ソウルツリーの「一個飛ばし」

### 根本原因 (特定済み)

`SoulTreeScreen.positions()` はノード座標を**ハードコードした極座標**で持つ。一方、枝線は `tree.json` の `prerequisites` から描く (`SoulTreeScreen.java:270`)。**この 2 つが対応していない。**

角度 120 のスポーク上に 4 ノードが並ぶ:

| ノード | 角度 | 半径 | 前提 |
|---|---|---|---|
| `phys_atk_up_1` | 120 | 200 | `root` |
| `card_grant_strong_strike` | 120 | 380 | `phys_atk_up_1` |
| `slot_expand_1` | 120 | 540 | `card_grant_strong_strike` |
| `phys_atk_up_2` | 120 | **700** | **`phys_atk_up_1`** |

`phys_atk_up_1` → `phys_atk_up_2` の枝線は、**同一角度上の `card_grant_strong_strike` と `slot_expand_1` を物理的に貫通する**。見た目は 200→380→540→700 の鎖だが、実際は 200→700 の直結。

結果、`phys_atk_up_1` を解放すると `card_grant_strong_strike` と `phys_atk_up_2` の**両方**が解放可能になり、`phys_atk_up_2` を先に取ると「間の 2 つを飛ばした」ように見える。**解放判定は正しい。**

角度 0 (HP 軸) では逆に、r200 の次が r700 で 380/540 が空。等間隔のリングを期待する目には「抜けている」と映る。

### 方針: 座標を前提グラフから導出する

ハードコード表を捨て、**半径 = 前提の深さ**で計算する。データが唯一の出所になり、`tree.json` を編集しても表が古くならない。

```
depth(root) = 0
depth(n)    = max(depth(p) for p in prerequisites(n)) + 1
radius      = RING_GAP * depth
angle       = 同じ depth のノードを均等配置 (親の角度に近い側へ寄せる)
```

これにより:
- 前提が 1 段違うノードは必ず 1 リング違う → 枝線が他ノードを貫通しない
- `phys_atk_up_2` は depth 2 なので `card_grant_*` と同じリングに来る (現状の r700 → r400)
- `layer_extend_4` は前提 2 つ (`hp_up_2`, `phys_atk_up_2`) の max + 1 = depth 3

### 完了条件

1. `positions()` のハードコード表を削除し、`tree.json` から導出する
2. **どの枝線も、両端以外のノードの描画円を通過しない** (自動テストで検証)
3. `tree.json` にノードを 1 件追加しても、座標表の手編集なしで正しく配置される
4. SOUL-02 で `slot_expand_*` が「魂の刻印」へ置換されても壊れない

### 検証方法

座標計算を LibGDX 非依存の純粋クラス (`SoulTreeLayout`) へ切り出し、次を単体テストする。

- 全ノードの depth が前提から正しく計算される
- 同一 depth のノードが重ならない (最小距離 > ノード直径)
- **全エッジについて、線分が両端以外のノード円と交差しない**

> 3 番目が本件の再発防止そのもの。現状はこれが無いため、座標を手で足すたびに同じ問題が起きうる。

### 注意

- `FeatureCatalog.md:511` は本件を「優先度低の描画不整合」として記録しているが、**プレイヤーには解放バグに見える**ため P1 へ格上げ済み
- 既存の `tryUnlockAt` は `LinkedHashMap` の挿入順に依存する旨のコメントがある (`SoulTreeScreen.java:135-136`)。座標導出へ変えるとき、この決定性を壊さないこと

## #1 敵ターンの表示

### 現状

`HudRenderer.java:347` が「敵のターン進行中…」を HUD へオレンジで常時表示するのみ。`ENEMY_STEP_INTERVAL = 0.10f` × 敵数ぶん入力できず、層 3 (敵 8 体) では理論上 2.4 秒以上。

### 方針

敵ターン開始時に**画面中央へ大きく短時間表示**し、フェードアウトさせる。常時出しっぱなしにはしない (視界を塞ぐため)。

- 表示位置: 画面中央上寄り (マップの視認を妨げない高さ)
- 表示時間: 0.6〜0.8 秒でフェードアウト。**敵ターンが続く間は HUD の既存表示が引き継ぐ**
- 既存の `ScreenEffects` (ダメージポップ・シェイクを持つ) に載せるのが自然

### 完了条件

1. 敵ターン開始で画面中央に大きく表示され、フェードアウトする
2. プレイヤーターン開始でも同様に表示する (どちらのターンか常に分かる)
3. 表示中もゲームは進行する (待たせない)
4. 既存の HUD 表示と二重に見えない

### 判断が要る点

**プレイヤーターンにも出すか。** 出すと「どちらのターンか」が常に分かるが、テンポの速いカードゲームでは煩わしくなりうる。デモ用途なら出す方が親切。**1 ラン試して決める。**

## #5 スケルトンの AI

### 現状 (仕様どおり)

`EnemyKind.SWIFT_SLIME` のみ `EnemyAiProfile.CAUTIOUS` (距離 2-3 を保つ kite 型、隣接されたら離れる)。他は全て `AGGRESSIVE`。スプライトは `DungeonScreen.java:167` で skeleton.png を割当。

**挙動は意図的**。問題は名称・見た目・挙動の三重のズレ。「はやスライム」という名前でスケルトンの見た目で逃げ回る。

### 方針: 名前を実像へ寄せる (レビュー §7.7 の結論)

画像を差し替えるとシルエット識別性が落ちる。**敵 ID と表示名を変える。**

| 現在 | 変更案 | 根拠 |
|---|---|---|
| `SWIFT_SLIME` / 「はやスライム」 / skeleton.png / CAUTIOUS | `SKELETON_ARCHER` 等 / 「スケルトン」/ 変更なし / 変更なし | 見た目と挙動 (距離を取る) の両方に合う |
| `TOUGH_SLIME` / 「かたスライム」 / goblin.png / AGGRESSIVE | `GOBLIN` / 「ゴブリン」 | 見た目に合わせる |

### 完了条件

1. 敵 ID・表示名・スプライト・AI 挙動の 4 つが互いに矛盾しない
2. `Bestiary` の保存値 (`EnemyKind.name()`) が変わるため、**旧セーブの移行**を用意する
3. `Fonts` のグリフ集合に新表示名の文字が含まれる

### 注意 (見落としやすい) — 波及範囲は Bestiary だけではない

`EnemyKind` を参照する本番コードは **24 箇所 / 8 ファイル以上**ある (実測)。

| ファイル | 依存の性質 |
|---|---|
| `ProfileData` / `ProfileDataMapper` | `defeatedEnemyKinds` に `EnemyKind.name()` を保存 |
| `SaveDataConverter` | `toBestiary` が未知名を **skip** する = 改名すると図鑑記録が**黙って消える** |
| `LegacySaveMapper` | 旧 save.json からの移行でも敵名を運ぶ |
| `InitialStateFactory` | 生成時の種別判定 |
| `Bestiary` / `Enemy` / `EnemyAiProfile` | ドメイン側 |

**移行が必須**。旧名 → 新名の対応表を `SaveDataConverter` と `LegacySaveMapper` の両方へ入れ、未知名 skip の前に読み替える。対応表を入れ忘れると、プレイヤーの図鑑が改名の瞬間に空になる。

> 保存系が安定した今が好機なのは事実だが、**SAVE 系に再び手を入れる**ことになる。第2バッチで P0 を 5 件作り込んだ領域なので、契約テストを先に足してから触ること。

## #2 壊れる壁の位置

### 現状

`placeBreakableWalls` は Wave 16 で「対向 2 方向が同時に FLOOR」= ショートカット壁を優先する改善済み。`isShortcutWall` は上下 or 左右が FLOOR なら true。

候補が 2 個未満のときだけ旧仕様 (内部 WALL 全部) の fallback へ落ちる。

### 仮説 (未検証)

1. `isShortcutWall` の条件が緩い。「上下が FLOOR」だけでは、壁の塊の縁でも成立し、壊しても通路が繋がらない場合がある
2. fallback へ落ちる頻度が高い
3. 条件は正しいが、**2〜3 個という個数**が少なく、有用な位置に当たる確率が低い

### 方針: まず計測する

推測で条件をいじる前に、**30 シードで実際の配置を集計**する。

- shortcutWalls の候補数の分布
- fallback へ落ちた回数
- 壊した結果、実際に**移動距離が短くなる**か

3 番目が本質。「ショートカットに見える壁」ではなく「壊すと本当に近道になる壁」を測る。

**測り方 (連結成分では測れない)**: BSP 生成のマップは元から全域が連結しているので、壁を 1 枚壊しても連結成分の数は変わらない。測るべきは**最短経路長の短縮量**。

```
壁 w について:
  d_before = BFS(spawn → stairs) を、w を WALL のまま計算
  d_after  = BFS(spawn → stairs) を、w を FLOOR に置換して計算
  有用度   = d_before - d_after   (0 なら壊しても無意味)
```

`spawn → stairs` だけでなく、`spawn → 各敵` の距離短縮も測ると「戦闘の選択肢が増えたか」まで見える。まずは階段までの短縮で足りる。

### 完了条件

1. 30 シードで、配置された壊れる壁の**過半数が到達距離を実際に短縮する**
2. fallback へ落ちる頻度を記録し、必要なら条件を緩める

> **推測で直さない。** Wave 16 で一度「改善した」ものが体感で効いていないので、同じ推測を重ねると三度目になる。
