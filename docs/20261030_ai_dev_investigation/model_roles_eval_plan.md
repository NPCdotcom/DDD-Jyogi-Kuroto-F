# AI の役割分担とモデル評価計画 (2026-10-30、提案。モデル比較の実行は未承認)

ラベル: [確認済み] 提供元の現行情報で確認 / [設計] 提案 / [見積り] 仮定に基づく概算 (確定値ではない)

## 1. 区別する 3 つの処理

| 区分 | 何を保証するか | 何を保証しないか | 例 |
|---|---|---|---|
| 決定的処理 (スクリプト) | 同じ入力なら同じ出力。計算が正確 | 曖昧な判断はできない | 集計・費用計算・指紋・ログ分類の規則部分・テスト結果の解析 |
| 通常 LLM の JSON Schema 出力 (structured outputs) | 出力がスキーマに適合する (構文と型) | **内容の正しさは保証しない** | Haiku 5.5、gpt-oss-20b などに schema を指定 |
| 構造化出力特化モデル | 特定の抽出タスク (例: HTML→JSON) に最適化 | 学習した領域外の判断・推論・日本語の質は未知 | `inference-net/schematron-v2-turbo` (説明: 3B の HTML-to-JSON 抽出モデル) |

原則: 件数・合計・費用・時間はスクリプトで確定させる。LLM の暗算や概算を計測値として扱わない。モデルが自己申告する confidence を正しさの根拠にしない。

## 2. 役割と担当 [設計]

| 役割 | 担当する仕事 | モデルの選び方 | 守ること |
|---|---|---|---|
| Lead | 設計、依存関係、優先順位、統合判断、最終報告 | 十分な推論能力を持つ通常 LLM (現行: Claude Opus 5.5) | サイクルごとに新しいセッションにする。Worker 報告は要約と該当箇所だけを読む (前回は全文読込を実測で確認) |
| Implementer | コード変更、テスト追加 | 既定は Codex (gpt-6.1-sol)。難易度に応じて Claude Sonnet/Opus | タスクごとに**独立クローン** (worktree は stash・refs を共有するため不十分。Critic v2 M05)。Codex は YOLO ではなくサンドボックス付きで起動する (承認 A5)。整形は変更ファイルに限定。`check` は 1 回 |
| Critic | 反証 | 実装担当と別のモデル系統、または別コンテキスト。価格を理由に格下げしない | 実装担当の結論の説明文ではなく、diff・受入条件・根拠の所在を渡す |
| 軽量 Worker | 分類、定型的な構造化判断、簡単な抽出 (失敗を検出でき、再実行できるものに限る) | §4 の評価に合格したモデルだけ | 合否ゲートに使わない。スキーマ検証と決定的な照合を必ず通す。UNKNOWN を許可する |
| 決定的処理 | 計測、集計、指紋、テスト結果の分類、権限ルール | スクリプト | fixture テストでバージョン管理する |

### このプロジェクトでの仕事の割り当て

| 仕事 | 担当 | 理由 |
|---|---|---|
| Gradle とテストの失敗分類 | 決定的 (C-1 の分類器) | 終了コード・タスク表示・XML で判定でき、LLM は不要 |
| 破壊的コマンドの判定 | 決定的 (権限ルール + Hook) | 誤判定の害が大きく、毎回のレイテンシも増やせない |
| 費用・時間の計測 | 決定的 (`metrics_v2.py`) | 数値の正確さが必要 |
| レビュー指摘の分類 (種類・重大度・人間判断の要否) | 軽量 Worker の候補 (評価 E1 次第) | 曖昧だが、誤りを検出・修正しやすい |
| 計測結果の文章化 (数値はスクリプトから) | 軽量 Worker の候補 (評価 E2 次第) | 入力にない数値の混入を決定的に検査できる |
| カード画像の読み取り・意味判定 | 視覚に強い中位以上のモデル | 軽量 Worker の範囲外 |
| 実装 | Implementer | — |
| 敵対的レビュー | Critic | — |

## 4. 採用前の評価計画 [設計・未実行]

### 4.1 代表タスクと正解データ (作成に API 費用はかからない)

| ID | タスク | 入力 | 正解の作り方 | n |
|---|---|---|---|---|
| E1 | レビュー指摘の分類 {種類, 重大度, 人間判断の要否} | 既存の指摘文 (UI/UX 監査 25、Critic 12、8/14 敵対的レビュー 6、本回の Critic 指摘) | Lead が付けた案を人間が確認して確定 | 約 50 |
| E2 | 計測結果の文章化 (日本語) | `metrics_v2` の出力 | **事実単位の照合** (Critic v2 M07): 文中の各記述を {対象, 期間, 指標, 値, 単位, 実測/推定/API 換算/請求の区別, 成否} に分解し、正解と照合する。決定的な検査 (入力にない数値を出さない、必須項目にすべて触れる) に加え、意味の正しさは人間が確認する | 約 30 (期間・セッションを変えて作成) |
| E3 | 失敗ログの分類 (対照実験) | 過去セッションの Gradle 出力 (FAILED 18・不明 12) と C-1 の fixture 出力 | C-1 の決定的分類器の結果を人間が確認 | 約 40 |

E3 は、決定的処理で足りるという仮説の確認用。LLM が勝てない場合は採用しない。

### 4.2 比較する構成

決定的なベースライン (E3 のみ)、Haiku 5.5、gpt-oss-20b、mistral-nemo、schematron-v2-turbo (E1・E3 のみ)、Sonnet 5.5 (参照)。各項目を 3 回ずつ実行し、ばらつきを見る。

### 4.3 指標

- 正解率、macro-F1。
- **重大な誤りの率**: E1 では Blocker/Major を Minor 以下に下げること、または人間判断の要否の取り違え。E2 では意味の反転 (失敗を成功と書く等)、対象や期間の取り違え、推定を実測と書くこと、API 換算を請求額と書くこと。E3 では失敗を成功と判定すること。
- 棄権 (UNKNOWN) は、正解率では「不正解」として分母に含める。受理費用の計算では、棄権した項目を参照モデルで再処理した費用を加算する。3 回の反復は同じ項目の繰り返しであり、独立した 3 倍の正解データとしては扱わない (ばらつきの評価にだけ使う)。
- スキーマ適合率。曖昧な項目で UNKNOWN を返した率。
- レイテンシ (p50/p95)。
- 1 項目あたりのトークン数と費用 (再試行を含む総額)。
- confidence はゲートに使わない。収集する場合も、正解との較正を見るだけにする。

### 4.4 事前に決める判定規則

軽量モデルをある仕事に採用するのは、次の 4 条件をすべて満たす場合だけ:
1. 正解データで重大な誤りが 0 件。
2. 正解率が参照 (Sonnet 5.5) から 5 ポイント以内 (n が小さいため暫定)。
3. スキーマ適合率 99% 以上、p95 レイテンシ 10 秒以内。
4. 再試行を含めた「受理できた 1 項目あたりの総費用」が参照より低い。

満たさなければ、決定的処理か参照モデルを使う。結果は探索的なものとして扱い、タスクの性質が変わったら再評価する。

### 4.5 費用の見積り [見積り: 仮定に基づく]

- 仮定: 1 項目あたり入力 1,500・出力 300 トークン、E1+E2+E3 の約 120 項目 × 3 回 = 360 呼出/モデル。
- 公開単価で計算すると、Haiku 5.5 で約 $0.11、Sonnet 5.5 で約 $2.16、gpt-oss-20b・mistral-nemo・schematron (E2 を除く 270 呼出) は各 $0.05 未満。合計 $2.33、再試行の余裕を 1.5 倍とみて $3.50 (Critic v2 が独立に検算して一致)。上限は承認時に設定する。
- 実額は、実行時に API の usage と請求画面で確認する (この見積りを実額として報告しない)。

### 4.6 承認が必要な事項

- 実行の可否と予算の上限。
- 認証情報: Anthropic API キーまたは OpenRouter キー (新しい認証情報の要求になる)。
- **外部送信**: 評価データ (レビュー指摘・計測結果・ログの抜粋) を外部の提供元へ送る。プロジェクト内部の情報を含むため、送信してよい範囲と、提供元のデータ取り扱い (ログ保存・学習利用の有無) を確認する。
- 正解ラベルの確定に要する人間の作業時間 (E1 で約 50 件)。

## 5. 全部高性能・全部低価格の評価 (前回 D-3 の修正版)

- 全部を高性能モデルにする案: 過去セッションでは API 換算額の大半がコンテキストの書込と読込だった ([実測] 1 セッション)。機械的な工程まで高単価で処理するのは無駄が大きい。対策は単価より先に、コンテキストの長さと重複作業を減らすこと。
- 全部を低価格モデルにする案: Opus 5.5 と Haiku 5.5 の出力単価の差は、入力 10 万トークン以下で 40 倍、超過時で 8 倍 ([確認済み] 公式価格。Critic v2 N05 で条件を追加)。反復が増えても、トークン代の差はすぐには消えない。本当のリスクは、①誤った PASS で欠陥が実機まで漏れること、②人間の確認と修正の時間、③上位モデルへ引き継ぐ際の再読込、④Gradle の再実行 (過去セッションでは失敗後の再実行が 18 回・14.3 分 [実測])。したがって比較は「受理できた成果 1 件あたりの総費用・時間・後から見つかった欠陥」で行う。
